# 讲义写作规范

本规范服务于《大模型推理服务：从算子到系统》。目标不是让十六章长得完全一样，而是保证它们具有同样的技术严谨度和教材可读性。

## 1. 写作对象与边界

默认读者学过 Python 和基础深度学习，知道矩阵乘和 Transformer 的大致结构，但没有独立写过 CUDA kernel，也没有实现过在线推理引擎。

讲义负责解释：

- 问题为什么出现；
- 机制怎样工作；
- 公式、张量 shape、代码和硬件怎样对应；
- 方案改善了什么，又付出了什么代价；
- 在哪些边界条件下结论不成立。

讲义不负责环境安装、逐条操作命令、提交文件、截图要求、评分点和验收流程。这些内容统一进入实验任务书。正文可以阅读工程代码，但代码用于解释机制，不用于代替讲解。

## 2. 一章应当形成一条叙事线

每章选择一个贯穿始终的问题。比如：

- CUDA 章追踪“一个 Tensor 怎样真正到达 GPU kernel”；
- GEMM 章追踪“一个 Linear 层为什么不断重复读取同一批数据”；
- Paged KV 章追踪“两个长度未知的请求怎样共享有限的显存块”；
- Continuous Batching 章追踪“新请求为何不必等整批请求全部结束”。

不要把章节写成术语词典。每引入一个概念，都要说明它在主问题中的位置，并用过渡句连接前后推理。

## 3. 推荐的章节骨架

下面是可裁剪的骨架，不是必须逐字使用的标题模板：

1. 用一个具体场景、反常现象或失败案例开篇。
2. 给出本章问题和读完后应具备的能力。
3. 建立最小心智模型，画出数据流或时间线。
4. 用一个带具体数字和 shape 的例子逐步推导。
5. 进入实现，解释关键代码而不是整段粘贴源码。
6. 从朴素方案推进到优化方案，保留“为什么需要下一步”的证据。
7. 讨论性能、容量、正确性或公平性的取舍。
8. 给出常见错误、反例和适用边界。
9. 用章末小结和思考题收束。

标题必须表达内容，例如“最后 24 个线程为什么必须停下来”，不要反复使用“背景知识”“原理详解”“实验中的少量对照”。

## 4. 概念、公式与 Shape

术语第一次出现时给出中文含义、英文全称和它解决的问题。不要连续堆叠缩写。

公式使用 Markdown/LaTeX，并在紧邻公式的位置解释每个符号。矩阵和张量必须标出 shape 及各维含义。例如：

```text
Q: [batch, num_heads, query_len, head_dim]
K: [batch, num_kv_heads, context_len, head_dim]
```

复杂公式至少配一个小规模数值例子。推导不能从定义直接跳到结论；如果省略步骤，要说明省略了什么以及为什么不影响本章重点。

指标必须给出测量边界。TTFT、TPOT、吞吐、显存占用和利用率都要说明起点、终点、分母与聚合方式。项目内部的代理量不得冒充行业通用指标。

## 5. 代码怎样进入讲义

代码块只承担以下任务之一：

- 暴露机制的最小核心；
- 展示错误与修正的差别；
- 连接公式和工程对象；
- 帮助读者追踪一次真实执行。

代码前先说明要观察什么，代码后解释关键行造成的状态变化。避免粘贴几十行后只说“代码如上”。正文使用经过删减的代码，给出工程文件路径供读者查看完整实现。

所有性能代码必须区分 warmup、同步和测量区间。所有 CUDA 接入示例必须区分 reference 正确与强制 CUDA 路径真实执行。

## 6. 图和表怎样使用

一张图只承担一个主要结论。图题应能独立说明读者要看什么，例如“逻辑 token 6 通过 block table 到达物理 slot 10”。

优先使用：

- 时间线：解释 prefill/decode、调度和并发；
- 数据流图：解释 Python、C++、launcher、kernel；
- 内存布局图：解释 tile、KV cache、block table；
- 状态机：解释请求、block ownership 和错误恢复；
- 表格：比较少量维度明确的方案。

可复用素材放在 `assets/weekXX/`。源文件、导出图片和 PPT 使用同一编号，例如 `fig03-02_tensor_to_kernel.*`。正文中的 Mermaid 可在定稿阶段导出为 SVG/PNG，PPT 不重新绘制另一份含义不同的图。

## 7. 避免机器式文风

以下写法需要主动删除：

- 每节都以“本节主要介绍……”开头；
- 同一结论换词重复三遍；
- 大量使用“不是……而是……”制造虚假对比；
- 把显然相关的名词排成十几项列表，却不解释因果；
- 用“非常重要”“显著提升”代替数据和机制；
- 每章套用完全相同的三级标题；
- 用总结语气扩写论文摘要，却没有推导、代码或边界。
- 用连续的设问句充当标题，例如“到底发生了什么”“为什么已经往下走了”；
- 用“三本账”“碰运气”“偷偷覆盖”等口语比喻代替准确的技术术语；
- 为了显得亲切而频繁使用“先看”“可以想象”“不妨”“很容易发现”。

段落应围绕一个判断展开。连续三个以上短列表通常说明叙事被切碎，应改写为推导、图或完整段落。

## 8. 事实与引用

每章在动笔前建立来源清单。参考资料按以下优先级选择：

1. 原始论文和会议版本；
2. 硬件、框架或系统项目的官方文档；
3. 官方教程、设计文档和维护者技术文章；
4. 高质量大学课程或公开教材；
5. 二手技术文章，仅用于补充理解，不作为关键事实的唯一依据。

硬件规格、框架 API、论文机制和课程项目实现必须明确区分。正文在相关论述之后就近插入链接，不把全部来源堆到章末，也不使用“据有关资料”等无法核查的措辞。

来源的作用是提供事实、定义、图表线索和论证框架，不是授权复制正文。即使给出链接，也不得大段翻译或改写得与原文高度相似。讲义应综合多个来源，用课程自己的例子、推导和工程代码重新组织；需要直接引用时，只保留必要的短句并明确标示。

借鉴外部教材时只复用教学方法，不复制文字、图或错误。发现来源与项目行为不一致时，以可复现实验和源码为准，并在正文中说明适用版本。

每章至少区分三类陈述：

- **通用原理**：由论文或官方技术文档支持；
- **上游实现**：明确指出对应项目和版本，不把某一版实现写成永恒定义；
- **课程实现**：链接到本工程源码，并明确简化项、缺失能力和适用范围。

## 9. 章末质量检查

定稿前逐项确认：

- 本章是否有一个清楚的主问题？
- 是否至少有一个完整的数值或 shape 算例？
- 图、表和代码是否各自承担解释任务？
- 是否从现象推到原因，而非只列结论？
- 是否说明方案代价和失效条件？
- 是否混入实验命令、提交要求或评分标准？
- 术语、符号和指标口径是否与前章一致？
- 章末问题是否能检查理解，而非让学生抄原句？

字符数、图数和代码块数只用于发现异常，不作为机械配额。典型章节可以有 6000 至 10000 个中文字符、4 至 8 张图表和 2 至 5 个核心代码片段，但内容需要决定最终长度。
